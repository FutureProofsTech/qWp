# QHS-5 — 512-bit Hash Stateful Signature

**Status:** Design accepted; implementation and local evidence complete; 1-hour soak passed.

**Security target:** 256-bit classical and ~128-bit quantum, 256 signatures per
key, no leaf reuse.

**Rule:** No external standard is accepted as proof. This document is the proof.

---

## 1. Parameters

| Parameter | Value |
|---|---:|
| Hash | 512-bit BLAKE3 mode (`H64`) |
| WOTS chains | 89 (86 message + 3 checksum) |
| WOTS chain length | 63 steps |
| Merkle height | 8 |
| Leaves / signatures | 256 |
| Public key | 72 bytes |
| Private key | 72 bytes |
| Signature | **6,216 bytes** |
| Key header | `[6, 6, 8, 0]` |
| Signature header | `[6, 6, leaf_index LE]` |

Signature layout:

```
4 header | 5,696 WOTS (89 × 64) | 512 auth (8 × 64) | 4 checksum
```

## 2. 512-bit hash mode

The 512-bit hash is

\[
H64(x) = H32(0x00 \parallel x) \parallel H32(0x01 \parallel x),
\]

and the derive-key variant is

\[
H64_{\text{ctx}}(x) = H32_{\text{ctx}}(0x00 \parallel x) \parallel H32_{\text{ctx}}(0x01 \parallel x).
\]

The two halves are independent BLAKE3 instances with distinct one-byte domain
tags. The construction gives a 512-bit output with collision resistance
~`2^256` and preimage resistance ~`2^512`, assuming BLAKE3 is a random oracle /
PRF in the fixed contexts. Quantum: collision ~`2^128`, preimage ~`2^256`.

## 3. Keys

Public key (72 bytes):

```
0   1  version     // 6
1   1  algorithm   // 6
2   1  height      // 8
3   1  reserved    // 0
4   64 root
68  4  reserved    // 0
```

Private key (72 bytes):

```
0   1  version     // 6
1   1  algorithm   // 6
2   1  height      // 8
3   1  reserved    // 0
4   64 seed
68  2  next_leaf   // 0..=256, little-endian
70  2  reserved    // 0
```

The private key is stateful. Each signature consumes one leaf; the counter must
be persisted atomically before the signature is released. Reusing a leaf is a
security break.

## 4. Domain separation

- `qWp QHS-5 secret`
- `qWp QHS-5 chain`
- `qWp QHS-5 wots-pk`
- `qWp QHS-5 leaf`
- `qWp QHS-5 node`
- `qWp QHS-5 message`
- `qWp QHS-5 signature-checksum`

Each context is used through `H64`/`H64_ctx`.

## 5. WOTS

For leaf `i` and chain `j`:

\[
s_{i,j} = H64_{\text{secret}}(seed \parallel i \parallel j),
\]

\[
p_{i,j} = F^{63}(s_{i,j}),
\]

\[
P_i = H64_{\text{wots-pk}}(p_{i,0}\parallel\cdots\parallel p_{i,88}),
\]

\[
L_i = H64_{\text{leaf}}(i \parallel P_i).
\]

The Merkle tree has 256 leaves:

\[
N = H64_{\text{node}}(\text{left}\parallel\text{right}).
\]

The public root is the root of the height-8 tree.

## 6. Message digits

The message digest is

\[
D = H64_{\text{message}}(m).
\]

The first 86 base-64 digits encode the 512-bit digest with four leading zero
bits:

- the first digit uses digest bits 0..1 (value 0..3);
- the next 85 digits use digest bits 2..511 (six bits each).

The checksum is

\[
C = \sum_{k=0}^{85} (63 - d_k),
\]

with `0 <= C <= 5418`. It is encoded in three base-64 digits:

\[
d_{86} = C \gg 12,\quad
d_{87} = (C \gg 6) \mathbin{\&} 63,\quad
d_{88} = C \mathbin{\&} 63.
\]

The 89-digit vector is the WOTS message. The checksum guarantees that two
different messages cannot have a digit vector where one is componentwise
greater than the other without a compensating decrease.

## 7. Signing

1. If `next_leaf >= 256`, return `KeyExhausted`.
2. Compute the 256 leaves (or load the validated cache).
3. Compute the message digits.
4. For each of the 89 chains, reveal `F^{d_j}(s_{i,j})`.
5. Include the 8-node auth path for leaf `i`.
6. Increment `next_leaf` and persist the key before releasing the signature.

## 8. Verification

1. Parse the header, leaf index, WOTS signature, auth path, and checksum.
2. Reject unless the header is `[6, 6, leaf_index LE]` and `leaf_index < 256`.
3. Recompute the message digits.
4. WOTS-verify the 89 chains.
5. Compute the leaf hash and climb the auth path.
6. Accept iff the root equals the public key root and the checksum matches.

## 9. Security proof

### Lemma 1 — Message-digit collision

The 86 message digits encode the full 512-bit digest injectively (four leading
zero bits, then 512 digest bits). Two distinct messages collide in the digit
vector only if they collide in `D`. The collision probability is at most
`2^-256` classically and `2^-128` quantum.

### Lemma 2 — WOTS one-time security

For a single leaf, the WOTS signature reveals one chain value per chain. A
forgery for a different digit vector requires decreasing at least one chain
value (a preimage of the 512-bit chain function) or exploiting the checksum
with a compensating decrease. The reduction loss is `89 × 63 = 5,607`, giving
approximately `2^499.5` classical preimage security, capped by the 256-bit
collision bound. Quantum preimage is ~`2^256`; the effective quantum bound is
~`2^128` from collision attacks.

### Lemma 3 — Merkle tree

A forged auth path that reaches the same root from a different leaf yields a
collision in `H64_leaf` or `H64_node`. The 512-bit output gives classical
collision ~`2^256` and quantum collision ~`2^128`. A second preimage is
~`2^512` classical.

### Lemma 4 — Stateful leaf uniqueness

Each leaf is used once. The counter is persisted atomically before the
signature is released; the CLI keyed state guard detects rollback when the
guard is ahead of the key counter. If the key and guard are restored together,
local software cannot detect rollback without a hardware monotonic counter;
that limitation is documented.

### Theorem — QHS-5 EUF-CMA

For at most 256 signing queries with unique leaves, QHS-5 is existentially
unforgeable under chosen-message attack, assuming the 512-bit BLAKE3 mode is a
PRF and is preimage- and collision-resistant. The dominant classical term is
the 256-bit digit/Merkle collision bound; the quantum bound is ~128 bits.

## 10. Concrete security

- Message-digit collision: ~`2^256` classical / `2^128` quantum.
- WOTS one-time: ~`2^499.5` classical preimage; capped by the 256-bit
  collision bound.
- Merkle collision: ~`2^256` classical / `2^128` quantum.
- Merkle second preimage: ~`2^512` classical.
- Overall: **256-bit classical / ~128-bit quantum**.
- Signatures per key: 256; leaf reuse is forbidden.

## 11. Limitations

- Signature is 6,216 bytes, larger than the plan's 3,400-byte estimate; the
  estimate was based on 45 chains, which do not bind the full 512-bit digest.
- Signing/keygen are slower than QHS-2 because of 89 chains and 64-byte values.
- Stateful: the key counter must be persisted atomically; no concurrent
  multi-writer use.
- BLAKE3 security is an assumption; the proof is a written reduction.
- No standard compliance claim.
- The private key is protected by file permissions (`0600`), not a passphrase or
  HSM.

## 12. Attack plan

1. Reuse a leaf with a different message.
2. Forge a WOTS chain value or digit vector.
3. Tamper with the auth path or leaf index.
4. Roll back the key counter.
5. Cross-version confusion with QHS-1/2/3/3.1/4/4.2.
6. Checksum/parser confusion.
7. Timing/fault/DoS.
8. Measure the best-known attack cost.

If any attack succeeds, QHS-5 is broken; fix or stop. No standard fallback.

## 14. Safe optimization: reusable derive-key contexts

The 512-bit mode uses two BLAKE3 derive-key instances. Recomputing the
derive-key context hash on every chain step is pure overhead: the context is
constant for a whole signature/keygen. The implemented optimization precomputes
the context key once and reuses it for every chain, leaf, node, message, and
checksum hash.

This is byte-identical to the current construction:

- the context key is the same `H32(DERIVE_KEY_CONTEXT, context)` value;
- the per-half tags `0x00` and `0x01` are unchanged;
- the material bytes are unchanged.

No signature, key, cache, guard, proof, or format changes. Measured with the
reusable contexts:

- sequential keygen ≈0.61 s (≈35% faster);
- parallel keygen ≈0.09 s (≈31% faster);
- cached-leaf sign ≈1.5 ms (≈29% faster);
- verify ≈1.2 ms (≈34% faster).

The QHS-5 KAT hash is unchanged. Measurements are recorded in
`docs/evidence/qhs5-timing.txt`.

Rejected optimizations that would change the security/format contract:

- base-32/base-16 WOTS: faster keygen/sign but a larger signature and a new
  parameter proof;
- 66×64 base-256 WOTS: smaller signature but ~12× chain hashing;
- caching WOTS secret chains: would put secret material at rest and enlarge the
  attack surface;
- a full Merkle-tree cache: saves only the ~255 node hashes, a small fraction
  of a cached signature;
- parallel WOTS signing: thread overhead is comparable to the ~1–2 ms cached
  sign time, so it is not a clear win;
- a single BLAKE3 XOF state for 64 bytes: its 256-bit internal chaining value
  cannot honestly provide 256-bit collision resistance.
