# QHS-1 — Construction and Security Proof

**Status:** QHS-1 release candidate; implementation in `qwp-crypto::qhs`.<br>
**Variants:** QHS-2 (1,704 bytes), QHS-3 (1,832 bytes, 4,096/key), and QHS-3.1 (tree-cache profile) are separate variants; QHS-1 is unchanged. See `docs/07-qhs2.md`, `docs/10-qhs3.md`, and `docs/12-qhs31.md`.<br>
**Security target:** ≥128-bit classical, ≥64-bit quantum, under the stated hash assumptions.  
**Rule:** No external standard is accepted as proof. This document is the proof.

---

## 1. Parameters

| Parameter | Value |
|---|---:|
| Hash | BLAKE3, 32-byte output |
| WOTS chains | 67 |
| WOTS chain length | 15 steps |
| Message digest | 32 bytes → 64 nibbles |
| Checksum | 3 nibbles (max 960) |
| Merkle height | 8 |
| Leaves per key | 256 |
| Signatures per key | 256 (stateful) |
| Public key | 64 bytes |
| Private key | 64 bytes |
| Signature | 2408 bytes |

The signature size is `4 + 2144 + 256 + 4 = 2408` bytes:

```
version 1 | algorithm 1 | leaf index 2 | WOTS signature 2144 | auth path 256 | checksum 4
```

## 2. Construction

### 2.1 Domain separation

All hash calls use distinct BLAKE3 derive-key contexts:

- `qWp QHS-1 secret`
- `qWp QHS-1 chain`
- `qWp QHS-1 wots-pk`
- `qWp QHS-1 leaf`
- `qWp QHS-1 node`
- `qWp QHS-1 message`
- `qWp QHS-1 signature-checksum`

Let \(H_d(x)\) denote BLAKE3 derive-key with context \(d\) and input \(x\).

### 2.2 WOTS chains

For leaf \(i\in[0,255]\) and chain \(j\in[0,66]\):

\[
s_{i,j} = H_{\text{secret}}(\text{seed} \parallel i \parallel j),
\]

\[
p_{i,j} = F^{15}(s_{i,j}),\qquad F(x)=H_{\text{chain}}(x).
\]

The WOTS public-key hash is

\[
P_i = H_{\text{wots}}(p_{i,0}\parallel\cdots\parallel p_{i,66}).
\]

### 2.3 Message digits

\[
D = H_{\text{message}}(m) \in \{0,1\}^{256}.
\]

Split \(D\) into 64 nibbles \(d_0,\dots,d_{63}\). Define the checksum

\[
c = \sum_{k=0}^{63}(15-d_k) \in [0,960].
\]

Encode \(c\) as three nibbles \(d_{64},d_{65},d_{66}\) (12 bits, big-endian). The digit vector is \(d=(d_0,\dots,d_{66})\).

### 2.4 Merkle tree

\[
L_i = H_{\text{leaf}}(i \parallel P_i),
\]

\[
N = H_{\text{node}}(\text{left}\parallel\text{right}).
\]

The public key is the root \(R\) of the 256-leaf tree plus metadata. The authentication path for leaf \(i\) is the eight sibling hashes.

### 2.5 Signing

The signer maintains a stateful counter \(i\). For message \(m\):

1. Require \(i<256\).
2. Compute digits \(d\).
3. For each chain \(j\), compute \(\sigma_j = F^{d_j}(s_{i,j})\).
4. Compute the authentication path for leaf \(i\).
5. Assemble the signature and checksum.
6. Increment \(i\) and persist the private key.

### 2.6 Verification

1. Parse version, algorithm, leaf index, WOTS signature, auth path, checksum.
2. Recompute digits \(d\).
3. For each chain, compute \(p'_{j}=F^{15-d_j}(\sigma_j)\).
4. Compute \(P'_i = H_{\text{wots}}(p'_0\parallel\cdots\parallel p'_{66})\).
5. Compute \(L'_i = H_{\text{leaf}}(i\parallel P'_i)\).
6. Climb the auth path to a root \(R'\).
7. Accept iff \(R'=R\) and the checksum is valid.

## 3. Assumptions

1. **Preimage resistance:** given \(y\), it is infeasible to find \(x\) with \(F(x)=y\).
2. **Collision resistance:** it is infeasible to find \(x\ne x'\) with \(H_d(x)=H_d(x')\).
3. **Domain separation:** the contexts above are distinct and fixed.
4. **Stateful leaf invariant:** the signer never uses a leaf twice and never rolls back the counter.

These are explicit assumptions. They are not hidden behind a standard or an external audit.

## 4. Security proof

### Lemma 1 — WOTS one-time unforgeability

Let \(A\) be an adversary that receives the WOTS public key for leaf \(i\) and one signature on message \(m\), and outputs a valid signature on \(m'\ne m\) for the same leaf. Then we can find a preimage of \(F\) or a collision in one of the hash functions.

**Proof.**

Let \(d\) and \(d'\) be the digit vectors for \(m\) and \(m'\). Let

\[
c=\sum_{k=0}^{63}(15-d_k),\qquad c'=\sum_{k=0}^{63}(15-d'_k)
\]

be the numeric checksum values, encoded in the last three digits. If \(m'\ne m\), either some message digit decreases (and we are done), or some message digit increases. In the latter case \(c'<c\). The base-16 encoding of the smaller value \(c'\) is lexicographically smaller, so at its first differing checksum digit it decreases. Therefore there is at least one index \(j\) with \(d'_j<d_j\).

Guess \(j\) and \(d'_j\); this succeeds with probability at least \(1/(67\cdot15)\). Embed a random challenge \(z=F(x)\) at chain step \(d'_j+1\):

- set the value at step \(d'_j+1\) to \(z\);
- compute the public chain end \(p_j=F^{15-(d'_j+1)}(z)\);
- for all other chains, choose random secrets normally.

If \(d_j\le d'_j\), abort. Otherwise compute the signing value at step \(d_j\) by iterating \(F\) forward from \(z\); this is possible because \(d_j>d'_j\). The simulated signature is distributed as the real one.

The forgery supplies a value \(y\) at step \(d'_j\) for the same chain. Verification gives

\[
F^{15-d'_j}(y)=p_j=F^{15-d'_j}(x).
\]

If \(y=x\), we have found a preimage of \(z=F(x)\). If \(y\ne x\), following the two chains from \(y\) and \(x\) until they meet yields a collision in \(F\) (or a collision in the iterated function, which yields a collision in \(F\) at the first divergence). Thus the forgery yields either a preimage or a collision.

The reduction loses at most a factor \(67\cdot15\approx 2^{10}\). ∎

### Lemma 2 — WOTS key-only unforgeability

For an unused leaf, the adversary receives only \(P_i\). A valid signature yields chain values whose forward hashes equal the \(p_{i,j}\). Producing them without a signing query requires either a preimage of \(F\) at some chain step or a collision in \(H_{\text{wots}}\). This is the same argument as Lemma 1 with no signing query; it is at least as hard. ∎

### Lemma 3 — Merkle tree unforgeability

Assume the adversary can produce a valid signature for a leaf \(i'\) and message \(m'\) that was not signed. Then either:

- \(i'\) is a leaf that was never used, and the WOTS signature is a key-only forgery (Lemma 2); or
- \(i'\) was used for a different message, and the WOTS signature is a one-time forgery (Lemma 1); or
- the authentication path produces a different leaf/root relation, which yields a collision in \(H_{\text{leaf}}\) or \(H_{\text{node}}\).

In all cases, the forgery reduces to Lemma 1, Lemma 2, or a hash collision. ∎

### Theorem — QHS-1 EUF-CMA

For at most 256 signing queries, QHS-1 is existentially unforgeable under chosen-message attack, assuming:

- BLAKE3 is preimage- and collision-resistant for the domain-separated contexts;
- the stateful leaf invariant holds.

**Proof.** Each query consumes a distinct leaf. A forgery is either for a used leaf (Lemma 1), an unused leaf (Lemma 2), or a different Merkle path (Lemma 3). The reduction loss is at most \(256\cdot67\cdot15\approx 2^{18}\), which is absorbed by the 256-bit hash output. ∎

## 5. Concrete security

- BLAKE3 output: 256 bits.
- WOTS preimage security: ≈256 bits minus the reduction loss (~18 bits) → ≈238 bits.
- Merkle collision security: ≈128 bits (birthday bound on 256-bit hashes).
- Overall classical target: ≥128 bits.
- Quantum: Grover preimage ≈2^128; collision ≈2^85–2^128 depending on the model; the conservative target is ≥64 bits.

The overall security is therefore at least the 128-bit classical target, with a large preimage margin and a 128-bit collision bound.

## 6. Stateful-key invariant

QHS-1 is a **stateful** signature scheme. Reusing a leaf for two different messages breaks WOTS one-time security.

Rules:

1. The private key carries `next_leaf`.
2. `sign` refuses when `next_leaf >= 256`.
3. The caller must persist the updated private key atomically after every signature.
4. Cloning, restoring an old private key, or concurrent signing with the same key is forbidden.
5. After 256 signatures, generate a new key.

The implementation enforces (1)–(3) in the API; (4)–(5) are operational requirements documented in the FAD and CLI.

### 7.1 Performance implementation (non-normative)

The production path keeps the construction, keys, signature bytes, and proof above
exactly. Three implementation-only optimizations reduce latency:

1. **Public-leaf cache.** The CLI stores the 256 Merkle leaves \(L_i\) in an
   optional 8,260-byte file next to the private key. The cache contains only
   public Merkle commitments; it never contains WOTS secrets or the seed. It is
   validated against a derive-key fingerprint of the seed
   (`qWp QHS-1 cache fingerprint`, distinct from all signature contexts) and a
   keyed BLAKE3 MAC (`qWp QHS-1 cache mac`) before use. A missing, malformed, or foreign cache is ignored and the
   leaves are recomputed. The cache is written atomically with mode `0600`.
   Poisoned cache data cannot forge a signature: the verifier recomputes the
   Merkle root, so altered leaves yield an invalid signature, not a valid one.
2. **Parallel keygen.** The 256 leaves are independent pure functions of
   `(seed, leaf_index)`. Keygen derives them on up to 16 host threads and then
   builds the same root as sequential derivation. A test asserts the parallel
   and sequential leaf arrays and keys are identical.
3. **Cached signing.** `sign_with_leaves` uses the supplied leaves only to build
   the authentication path. The WOTS signature still comes from the secret seed,
   the counter advance is unchanged, and the emitted signature bytes are
   identical. `sign` remains available and recomputes the leaves.
4. **Key state guard.** The CLI writes a keyed `<private-key>.state` guard. If
   the guard counter is ahead of the key counter, signing is refused as a
   rollback; a missing guard is rebuilt. This detects accidental restoration of
   an old key backup.

Measured on the 16-thread reference host with the release build and
`qwp-timing`:

| Operation | Sequential implementation | Optimized implementation |
|---|---:|---:|
| Keygen | ≈122 ms | ≈10–13 ms |
| Sign | ≈122 ms | ≈0.21–0.33 ms |
| Verify | ≈0.14 ms | ≈0.14 ms |

The timing harness reports Welch \(|t| < 4.5\) for keygen and signing across two
secret seeds. The QHS-1 known-answer signature hash is unchanged:
`662fbe8fa1196d087c6a9fe404ec146418424ae068cedb544328b7ac0c8c3eb9`.

The optimization changes no parameter, assumption, proof step, signature byte,
or stateful-key rule. It is outside the security argument and cannot weaken it.

## 8. Limitations

- BLAKE3 security is an assumption; qWp implements and tests BLAKE3 but does not prove its cryptographic hardness.
- The proof is a written reduction, not a machine-checked cryptographic proof.
- The scheme is stateful and limited to 256 signatures per key.
- No standard compliance claim is made.
- The braid/Jones engine is a research module and is not part of the QHS-1 security argument.

## 9. Attack plan

1. Forge a signature for a used leaf (Lemma 1 attack).
2. Forge for an unused leaf (key-only WOTS attack).
3. Tamper with auth path/leaf index.
4. Reuse a leaf by rolling back the counter (must be prevented operationally).
5. Exhaust the key and verify rejection.
6. Cross-domain hash confusion.
7. Timing/fault/DoS.
8. Measure the best-known attack cost and publish it.

If any attack succeeds, QHS-1 is broken; fix or stop. No standard fallback.
