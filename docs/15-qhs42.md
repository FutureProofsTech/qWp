# QHS-4.2 — Compact Stateless Hypertree/FORS Signature

**Status:** Design accepted; implementation in progress.

**Security target:** 128-bit classical and at least 64-bit quantum for
`q ≤ 2^20` signatures per key.

**Rule:** No external standard is accepted as proof. This document is the proof.

---

## 1. Parameters

| Parameter | Value |
|---|---:|
| Hash | BLAKE3, 32-byte output |
| WOTS base | 256 |
| WOTS chains | 34 (32 message + 2 checksum) |
| WOTS chain length | 255 steps |
| Hypertree layers | 7 |
| Subtree height | 8 |
| Total height | 56 |
| FORS trees | 17 |
| FORS height | 8 (256 leaves/tree) |
| Public key | 68 bytes |
| Private key | 68 bytes |
| Signature | **14,344 bytes** |
| Header | `[5, 5, 56, 0]` |

Signature layout:

```
4 header | 32 randomizer | 4,896 FORS | 9,408 hypertree | 4 checksum
```

- FORS: `17 × (32 + 8×32) = 4,896`.
- Hypertree: `7 × (1,088 WOTS + 256 auth) = 9,408`.
- WOTS signature: `34 × 32 = 1,088` per layer.
- Checksum covers the first 14,340 bytes.

## 2. Keys

Private key (68 bytes):

```
0   1  version     // 5
1   1  algorithm   // 5
2   1  height      // 56
3   1  reserved    // 0
4   32 SK.seed
36  32 PK.seed
```

Public key (68 bytes):

```
0   1  version     // 5
1   1  algorithm   // 5
2   1  height      // 56
3   1  reserved    // 0
4   32 PK.seed
36  32 root
```

`SK.seed` and `PK.seed` are derived from a 32-byte keygen seed with distinct
QHS-4.2 derive-key contexts. There is no counter, cache, or state guard.

## 4. Hypertree

A 56-bit path `idx` selects:

- layer `l = 0..6` (0 = bottom, 6 = top);
- leaf index `(idx >> 8l) & 0xff`;
- tree index `idx >> 8(l+1)` for `l < 6`, and `0` for the top layer.

Each layer is a binary tree of height 8. The top tree (layer 6, tree index 0)
is computed at keygen; its root is the public key. Lower trees are generated on
demand during signing.

WOTS key derivation:

\[
s_{l,t,i,j} = H_{\text{wots secret}}(SK.seed \parallel PK.seed \parallel l \parallel t \parallel i \parallel j),
\]

\[
p_{l,t,i,j} = F^{255}(s_{l,t,i,j}),
\]

\[
P_{l,t,i} = H_{\text{wots-pk}}(p_{l,t,i,0}\parallel\cdots\parallel p_{l,t,i,33}),
\]

\[
L_{l,t,i} = H_{\text{leaf}}(l \parallel t \parallel i \parallel P_{l,t,i}),
\]

\[
N = H_{\text{node}}(\text{left}\parallel\text{right}).
\]

The WOTS message is hashed with `H_wots-message` to 32 bytes. The 32 bytes are
the 32 base-256 message digits. The checksum is

\[
C = \sum_{j=0}^{31} (255 - d_j),
\]

encoded in two base-256 checksum digits `C >> 8` and `C & 0xff`. The checksum
range is `0..=8160`, which fits 16 bits.

The bottom WOTS key signs the fixed FORS public key for that leaf. Upper WOTS
keys sign the fixed root of the tree below. WOTS reuse therefore repeats the
same message, not two different messages.

## 5. FORS

For a bottom leaf `(tree_index, leaf_index)`, the FORS key is fixed. FORS has
17 trees of 256 leaves:

\[
s_{i,j} = H_{\text{fors secret}}(SK.seed \parallel PK.seed \parallel tree\_index \parallel leaf\_index \parallel i \parallel j),
\]

\[
L_{i,j} = H_{\text{fors leaf}}(i \parallel j \parallel s_{i,j}),
\]

\[
R_i = \text{Merkle root of } L_{i,0..255},
\]

\[
FORS\_PK = H_{\text{fors-pk}}(R_0\parallel\cdots\parallel R_{16}).
\]

The FORS digest is

\[
D = H_{\text{fors digest}}(R \parallel PK.seed \parallel m).
\]

The first 17 bytes of `D` are the selected leaf indices `d_0..d_16`. The FORS
signature reveals `s_{i,d_i}` and the 8-node authentication path in each tree.
The verifier recomputes each root and `FORS_PK`.

The hypertree index is

\[
idx = H_{\text{tree index}}(R \parallel PK.seed \parallel m),
\]

where the first 8 bytes are interpreted little-endian. `idx` selects the bottom
leaf and all seven layer positions.

## 6. Signing

1. `R = H_randomizer(SK.seed || m)`.
2. Compute `D`, `idx`.
3. Select the bottom leaf `(t_0, i_0)` and compute its fixed FORS key.
4. Produce the FORS signature on `D`.
5. For layer `0..6`:
   - select `(t_l, i_l)`;
   - message = `FORS_PK` for layer 0, otherwise the root of layer `l-1`;
   - hash the message with `H_wots-message`, encode 32+2 base-256 digits;
   - WOTS-sign with the fixed key at `(l, t_l, i_l)`;
   - include the 8-node auth path.
6. Assemble the signature, set the header `[5, 5, 56, 0]`, and append the
   checksum.

No counter is read or written. The private key is unchanged after signing.

## 7. Verification

1. Parse the 4-byte header, 32-byte randomizer, FORS signature, seven layer
   signatures, and 4-byte checksum.
2. Reject unless the header is exactly `[5, 5, 56, 0]` and the checksum matches
   the first 14,340 bytes.
3. Recompute `D` and `idx`.
4. Verify FORS to obtain `FORS_PK`.
5. For each layer `0..6`, hash the layer message, WOTS-verify the layer
   signature, compute the leaf, climb the auth path, and obtain the layer root.
6. Accept iff the top root equals the public key root.

The checksum is a corruption check, not a MAC. Authentication comes from the
WOTS/FORS hash chains and the Merkle paths.

## 8. Security proof

### Lemma 1 — WOTS fixed-message security

Each WOTS key signs one fixed 32-byte value. Reusing the key repeats the same
deterministic signature. A forgery for a different value at the same WOTS key
requires a preimage or second preimage in the chain function `F`, with loss at
most `34 × 255 = 8,670 ≈ 2^13.08`. With a 256-bit hash output, the WOTS
fixed-message advantage is approximately `2^-242.9`. The 128-bit overall cap
comes from hash collisions in the Merkle/FORS trees, not from this term.

### Lemma 2 — FORS few-time security

For one FORS key, after `γ` signatures on the same bottom leaf, the adversary
has seen at most `γ` leaves per FORS tree. A forgery requires a digest whose 17
indices all point to revealed leaves. For a random digest, this probability is
at most

\[
\left(\frac{\gamma}{256}\right)^{17}.
\]

For `γ = 1` this is `2^-136`; for `γ = 2`, `2^-119`.

The bottom leaf is a 56-bit value derived from the randomizer, `PK.seed`, and
the message. To use a revealed FORS key, the forgery must first hit one of the
`q` previously used bottom leaves, which costs at most `q / 2^56`. For
`q ≤ 2^20` and `γ = 1`, the per-attempt forgery probability is therefore at
most

\[
\frac{q}{2^{56}} \cdot 2^{-136} = 2^{-172}.
\]

The digest is a PRF/random-oracle output, so the adversary cannot force a
favorable digest except with the stated probability.

### Lemma 3 — Hypertree path reuse

A bottom leaf is reused only if two signatures share the full 56-bit path
`idx`. For `q` signatures, the union bound is

\[
\Pr[\text{path collision}] \le \frac{q(q-1)}{2^{57}}.
\]

For `q ≤ 2^20`, this is at most `2^-17`. If a collision occurs, the FORS key is
used twice; Lemma 2 bounds the resulting forgery probability by `2^-119`.
The product is `2^-136`. Upper-layer WOTS keys always sign fixed roots, so their
reuse is harmless.

### Lemma 4 — Merkle path unforgeability

A forged auth path that reaches the same root from a different leaf yields a
collision in `H_leaf` or `H_node`. With a 32-byte hash output, the classical
collision bound is 128 bits. The FORS roots and the public hypertree root are
protected by the same collision bound.

### Theorem — QHS-4.2 EUF-CMA

For at most `q ≤ 2^20` signing queries, QHS-4.2 is existentially unforgeable
under chosen-message attack, assuming BLAKE3 is a PRF and is preimage- and
collision-resistant for the fixed contexts.

**Proof.** A forgery is either a FORS forgery (Lemma 2), a WOTS forgery on a
fixed value (Lemma 1), a hypertree path forgery (Lemma 3/4), or a
checksum/parser failure. The dominant terms are the 136-bit FORS one-time
bound, the 128-bit Merkle/FORS collision bound, and the `2^-136` leaf-reuse
term. The construction targets the 128-bit classical level for `q ≤ 2^20`; the
`2^-128` collision term is the limiting bound. ∎

## 9. Concrete security

- FORS one-time (one revealed leaf per tree): `2^-136`.
- FORS forgery against `q` used leaves: at most `q · 2^-192`; for `q = 2^20`,
  `2^-172`.
- FORS leaf reuse after a 56-bit path collision: `2^-17 · 2^-119 = 2^-136`.
- WOTS fixed-message: approximately `2^-242.9` (preimage reduction); capped by
  the tree collision bound.
- Merkle/FORS collision: approximately 128 bits classical.
- Overall classical: the 128-bit security level for `q ≤ 2^20` (the `2^-128`
  collision term is the limiting bound).
- Quantum: Grover preimage ≈`2^128`; collision ≈`2^85`; FORS index search
  ≈`2^68`; bottom-leaf selection ≈`2^28`; conservative bound at least 64 bits.

QHS-4.2 is stateless, but the security bound is finite in `q`; the documented
limit is `2^20` signatures per key.

## 10. Limitations

- Signature is 14,344 bytes (≈21% smaller than QHS-4/4.1).
- WOTS chain length 255 makes signing ≈2.7× slower than QHS-4.1; parallel
  signing is still available.
- Stateless but bounded to `q ≤ 2^20`.
- BLAKE3 security is an assumption; the proof is a written reduction.
- No standard compliance claim.
- QHS-4.2 is newer than QHS-4/4.1.
- The private key is protected by file permissions (`0600`), not a passphrase or
  HSM.

## 11. Attack plan

1. Forge FORS after one or more signatures on the same leaf.
2. Reuse a bottom WOTS key with different FORS public keys.
3. Forge an upper WOTS key (must be fixed-message).
4. Tamper with auth paths, tree indices, or leaf indices.
5. Cross-version confusion with QHS-4/4.1.
6. Checksum/parser confusion.
7. Timing/fault/DoS.
8. Measure the best-known attack cost.

If any attack succeeds, QHS-4.2 is broken; fix or stop. No standard fallback.
