# QHS-3 — High-Capacity Stateful Hash-Based Signature

**Status:** QHS-3 release candidate; QHS-1, QHS-2, and QHS-3.1 remain available.<br>
**Security target:** ≥128-bit classical, ≥64-bit quantum, under the stated hash assumptions.  
**Rule:** No external standard is accepted as proof. This document is the proof.

---

## 1. Parameters

| Parameter | Value |
|---|---:|
| Hash | BLAKE3, 32-byte output |
| WOTS chains | 45 |
| WOTS chain length | 63 steps |
| Message digits | 43 base-64 digits |
| Checksum | 2 base-64 digits (max 2709) |
| Merkle height | 12 |
| Leaves per key | 4,096 |
| Signatures per key | 4,096 (stateful) |
| Public key | 64 bytes |
| Private key | 64 bytes |
| Signature | 1,832 bytes |

The signature size is `4 + 1440 + 384 + 4 = 1832` bytes:

```
version 3 | algorithm 3 | leaf index 2 | WOTS signature 1440 | auth path 384 | checksum 4
```

## 2. Construction

QHS-3 uses the QHS-2 WOTS construction and message encoding. The only
cryptographic parameter change is the Merkle height: 12 instead of 8.

### 2.1 Domain separation

- `qWp QHS-3 secret`
- `qWp QHS-3 chain`
- `qWp QHS-3 wots-pk`
- `qWp QHS-3 leaf`
- `qWp QHS-3 node`
- `qWp QHS-3 message`
- `qWp QHS-3 signature-checksum`

The cache fingerprint uses `qWp QHS-3 cache fingerprint`. These are distinct
from QHS-1, QHS-2, and QHS-3.1.

### 2.2 WOTS chains

For leaf \(i\in[0,4095]\) and chain \(j\in[0,44]\):

\[
s_{i,j} = H_{\text{secret}}(\text{seed} \parallel i \parallel j),
\]

\[
p_{i,j} = F^{63}(s_{i,j}),\qquad F(x)=H_{\text{chain}}(x),
\]

\[
P_i = H_{\text{wots}}(p_{i,0}\parallel\cdots\parallel p_{i,44}).
\]

### 2.3 Message digits

\[
D = H_{\text{message}}(m) \in \{0,1\}^{256}.
\]

Prefix two zero bits, split into 43 base-64 digits \(d_0,\dots,d_{42}\), and
encode the checksum

\[
c = \sum_{k=0}^{42}(63-d_k) \in [0,2709]
\]

as two base-64 digits \(d_{43},d_{44}\). The digit vector is
\(d=(d_0,\dots,d_{44})\). The checksum-decrease argument is identical to
QHS-2.

### 2.4 Merkle tree

\[
L_i = H_{\text{leaf}}(i \parallel P_i),
\]

\[
N = H_{\text{node}}(\text{left}\parallel\text{right}).
\]

The tree has 4,096 leaves and height 12. The authentication path is 12 sibling
hashes.

### 2.5 Signing and verification

Signing and verification are identical to QHS-2, with:

- 4,096 leaves instead of 256;
- 12 auth-path nodes instead of 8;
- a 2-byte leaf index (0..=4095).

## 3. Assumptions

1. **Preimage resistance:** given \(y\), it is infeasible to find \(x\) with \(F(x)=y\).
2. **Collision resistance:** it is infeasible to find \(x\ne x'\) with \(H_d(x)=H_d(x')\).
3. **Domain separation:** the contexts above are distinct and fixed.
4. **Stateful leaf invariant:** the signer never uses a leaf twice and never rolls back the counter.

## 4. Security proof

### Lemma 1 — WOTS one-time unforgeability

Identical to QHS-2 Lemma 1, with 45 chains of 63 steps. The reduction loses at
most \(45\cdot63=2835\).

### Lemma 2 — WOTS key-only unforgeability

Identical to QHS-2 Lemma 2.

### Lemma 3 — Merkle tree unforgeability

Identical to QHS-2 Lemma 3, over a height-12 tree with 4,096 leaves.

### Theorem — QHS-3 EUF-CMA

For at most 4,096 signing queries, QHS-3 is existentially unforgeable under
chosen-message attack, assuming BLAKE3 is preimage- and collision-resistant for
the fixed contexts and the stateful leaf invariant holds.

**Proof.** Each query consumes a distinct leaf. A forgery is either for a used
leaf (Lemma 1), an unused leaf (Lemma 2), or a different Merkle path (Lemma 3).
The reduction loss is at most

\[
4096\cdot45\cdot63 \approx 2^{21.47},
\]

which is absorbed by the 256-bit hash output. ∎

## 5. Concrete security

- BLAKE3 output: 256 bits.
- WOTS preimage security: ≈256 − 21.5 → ≈234.5 bits.
- Merkle collision security: ≈128 bits.
- Overall classical target: ≥128 bits.
- Quantum: Grover preimage ≈2^128; collision ≈2^85–2^128; conservative target ≥64 bits.

## 6. Stateful-key invariant

QHS-3 is stateful. Reusing a leaf breaks WOTS one-time security.

1. The private key carries `next_leaf` (0..=4096).
2. `sign` refuses when `next_leaf >= 4096`.
3. The caller must persist the updated key atomically after every signature.
4. Cloning, restoring an old key, or concurrent signing is forbidden.
5. After 4,096 signatures, generate a new key.

## 7. Implementation proof obligations

| Obligation | Evidence |
|---|---|
| Sizes exact | const assertions + tests |
| Parser rejects malformed metadata | unit + attack tests |
| WOTS digits/checksum correct | KAT + round-trip/attack tests |
| Sign/verify round-trip | unit + integration tests |
| Tamper/wrong message/wrong key rejected | attack suite |
| Key exhaustion rejected | attack suite |
| No panic/OOB/overflow | Kani + Miri + fuzz |
| Constant-time signing | timing harness + fixed-loop code review |
| State counter persisted | CLI/key-store tests |
| Cached leaves match sequential derivation | unit + parallel-equivalence tests |
| Cache validation and fallback | CLI cache tests |

### 7.1 Performance

Measured/projected on the 16-thread reference host:

| Operation | QHS-3 |
|---|---:|
| Keygen | ≈0.40–0.44 s |
| Cached sign | ≈1.60–1.70 ms |
| Verify | ≈0.39 ms |

Keygen scales linearly with the 16× larger leaf count; signing and verification
only add four extra auth-path hashes. The CLI also writes a keyed
`<private-key>.state` guard to detect counter rollback before signing.

## 8. Limitations

- Stateful and limited to 4,096 signatures per key.
- 128 KiB cache.
- BLAKE3 security is an assumption; the proof is a written reduction.
- QHS-3 is newer than QHS-1/QHS-2 and needs its own deployment evidence; QHS-3.1 shares its signature format.
- No standard compliance claim.

## 9. Attack plan

1. Forge a used-leaf signature.
2. Forge an unused-leaf signature.
3. Tamper with auth path or leaf index.
4. Roll back the counter / reuse a leaf.
5. Exhaust the key.
6. Cross-version confusion (QHS-1/QHS-2/QHS-3/QHS-3.1).
7. Cache poisoning.
8. Timing/fault/DoS.
9. Measure the best-known attack cost.

If any attack succeeds, QHS-3 is broken; fix or stop. No standard fallback.
