# QHS-4.1 — Parallel Fast-Signing Profile

**Status:** Implemented; local evidence complete; 1-hour soak passed.

**Relationship to QHS-4:** QHS-4.1 is a performance profile, not a new
parameter set. It uses the same keys, the same 18,216-byte signature, the same
header `[4, 4, 64, 0]`, the same proof, and the same `q ≤ 2^20` security bound.
Only the implementation is optimized.

---

## 1. Why the trees can be parallelized

For a message, QHS-4 first derives:

- the randomizer `R`;
- the FORS digest `D`;
- the 64-bit hypertree path `idx`.

After that, the eight hypertree subtrees and the sixteen FORS trees are
independent of the message:

- a hypertree leaf at layer `l`, tree `t`, leaf `i` depends only on
  `(SK.seed, PK.seed, l, t, i)`;
- a FORS leaf depends only on the bottom `(tree, leaf)` and the FORS tree/leaf
  indices.

The WOTS signatures depend on the child roots, but those roots are the
precomputed tree roots. The assembly is therefore:

1. compute all hypertree and FORS leaves (parallel);
2. build the eight subtree roots/auth paths and the sixteen FORS roots/auth
   paths;
3. verify the selected paths against the precomputed roots;
4. write the WOTS signatures and the same signature bytes.

## 2. Implementation

- `qwp-hash::DeriveKey`: reusable BLAKE3 derive-key context. It produces the
  same output as `derive_key32`; the context hash is computed once.
- `qwp-crypto::Qhs4Contexts`: the QHS-4 context set.
- `qwp-crypto::qhs4_signing_plan`: the message-specific plan (randomizer, FORS
  digest, path, layer positions).
- `qwp-crypto::qhs4_leaf` / `qhs4_fors_leaf`: public leaf primitives.
- `qwp-crypto::qhs4_tree_root_and_auth_from_leaves` /
  `qhs4_fors_root_and_auth_from_leaves`: tree builders.
- `qwp-crypto::qhs4_sign_with_trees`: verified signature assembly.
- `qwp-platform::qhs4_sign_parallel`: scoped-thread tree generation and
  assembly.
- `qhs41-*` CLI commands; `qhs4-verify` and `qhs41-verify` accept the same
  signatures.

The sequential `Qhs4PrivateKey::sign` remains the reference and fallback.

## 3. Equivalence argument

The optimization changes **when** hashes are computed, not **what** is hashed.

- `DeriveKey::hash32(material)` is exactly
  `derive_key32(context, material)`; the hash crate tests compare them for
  multiple contexts and materials, including streaming.
- `qhs4_leaf` and `qhs4_fors_leaf` use the same inputs and contexts as the
  sequential tree builder.
- The tree builders use the same node hashes and leaf ordering.
- `qhs4_sign_with_trees` re-derives the plan and checks the selected leaf path
  against each provided root before writing the signature. A mismatched plan or
  tree returns `InternalFailure`.
- The release test `sign_with_trees_matches_sequential` compares the assembled
  signature to `Qhs4PrivateKey::sign` byte-for-byte.
- The platform test `qhs4_parallel_sign_matches_sequential` does the same
  through `qhs4_sign_parallel`.

No new assumption or format is introduced. The QHS-4 proof applies unchanged.

## 4. Performance

Reference host, release build, 16-thread cap:

| Operation | QHS-4 sequential | QHS-4.1 parallel |
|---|---:|---:|
| Keygen | ≈0.096 s | ≈0.096 s |
| Sign | ≈0.815 s | **≈0.110 s** |
| Verify | ≈1.57 ms | ≈1.57 ms |
| Signature | 18,216 B | 18,216 B |
| Keys | 68 B | 68 B |

Measured speedup: **≈7.4×** for signing. The parallel path uses
`std::thread::scope` in `qwp-platform`; the crypto core stays `no_std`.

## 5. Security

- Same QHS-4 proof and parameters.
- Same `q ≤ 2^20` limit at the 128-bit classical target.
- Same hash contexts and signature bytes.
- No counter, no cache, no state guard; signing leaves the private key
  unchanged.
- No 2^64 variant is planned or claimed.

## 6. CLI

```bash
qwp qhs41-keygen public.key private.key
qwp qhs41-sign private.key message.txt message.sig
qwp qhs41-verify public.key message.txt message.sig
```

`qhs4-verify` accepts QHS-4.1 signatures, and `qhs41-verify` accepts QHS-4
signatures. The keys and signature format are identical.

## 8. Limitations

- The parallel path uses host threads and `std`; `no_std` users keep the
  sequential `sign`.
- The speedup depends on the host core count and scheduler.
- QHS-4.1 is not a new security parameter set and does not raise the
  `q ≤ 2^20` bound.
- The project remains non-standard and not externally audited.
