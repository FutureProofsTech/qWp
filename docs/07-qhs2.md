# QHS-2 — Smaller Hash-Based Signature

**Status:** QHS-2 release candidate; QHS-1, QHS-3, and QHS-3.1 remain available.<br>
**Security target:** ≥128-bit classical, ≥64-bit quantum, under the stated hash assumptions.  
**Rule:** No external standard is accepted as proof. This document is the proof.

---

## 1. Parameters

| Parameter | Value |
|---|---:|
| Hash | BLAKE3, 32-byte output |
| WOTS chains | 45 |
| WOTS chain length | 63 steps |
| Message digest | 256 bits |
| Message digits | 43 base-64 digits |
| Checksum | 2 base-64 digits (max 2709) |
| Merkle height | 8 |
| Leaves per key | 256 |
| Signatures per key | 256 (stateful) |
| Public key | 64 bytes |
| Private key | 64 bytes |
| Signature | 1,704 bytes |

The signature size is `4 + 1440 + 256 + 4 = 1704` bytes:

```
version 2 | algorithm 2 | leaf index 2 | WOTS signature 1440 | auth path 256 | checksum 4
```

## 2. Construction

### 2.1 Domain separation

All hash calls use distinct BLAKE3 derive-key contexts:

- `qWp QHS-2 secret`
- `qWp QHS-2 chain`
- `qWp QHS-2 wots-pk`
- `qWp QHS-2 leaf`
- `qWp QHS-2 node`
- `qWp QHS-2 message`
- `qWp QHS-2 signature-checksum`

These are distinct from every QHS-1 context. The cache fingerprint uses
`qWp QHS-2 cache fingerprint`.

Let \(H_d(x)\) denote BLAKE3 derive-key with context \(d\) and input \(x\).

### 2.2 WOTS chains

For leaf \(i\in[0,255]\) and chain \(j\in[0,44]\):

\[
s_{i,j} = H_{\text{secret}}(\text{seed} \parallel i \parallel j),
\]

\[
p_{i,j} = F^{63}(s_{i,j}),\qquad F(x)=H_{\text{chain}}(x).
\]

The WOTS public-key hash is

\[
P_i = H_{\text{wots}}(p_{i,0}\parallel\cdots\parallel p_{i,44}).
\]

### 2.3 Message digits

\[
D = H_{\text{message}}(m) \in \{0,1\}^{256}.
\]

Interpret \(D\) as a 256-bit big-endian integer, prefix two zero bits, and split
the resulting 258 bits into 43 base-64 digits \(d_0,\dots,d_{42}\). The first
digit is therefore in `0..=15`; the rest are in `0..=63`.

Define the checksum

\[
c = \sum_{k=0}^{42}(63-d_k) \in [0,2709].
\]

Encode \(c\) as two base-64 digits \(d_{43},d_{44}\) (big-endian). The digit
vector is \(d=(d_0,\dots,d_{44})\).

For any two distinct messages, either some message digit decreases, or some
message digit increases and the checksum decreases. The two-digit base-64
encoding of the smaller checksum is lexicographically smaller at its first
differing digit, so some checksum digit decreases. This is the same argument as
QHS-1, with a larger digit base.

### 2.4 Merkle tree

\[
L_i = H_{\text{leaf}}(i \parallel P_i),
\]

\[
N = H_{\text{node}}(\text{left}\parallel\text{right}).
\]

The public key is the root \(R\) of the 256-leaf tree plus metadata. The
authentication path for leaf \(i\) is the eight sibling hashes.

### 2.5 Signing

The signer maintains a stateful counter \(i\). For message \(m\):

1. Require \(i<256\).
2. Compute digits \(d\).
3. For each chain \(j\), compute \(\sigma_j = F^{d_j}(s_{i,j})\).
4. Compute the authentication path for leaf \(i\).
5. Assemble the signature and checksum.
6. Increment \(i\) and persist the private key.

### 2.6 Verification

1. Parse version, algorithm, leaf index, WOTS signature, auth path, checksum.
2. Recompute digits \(d\).
3. For each chain, compute \(p'_{j}=F^{63-d_j}(\sigma_j)\).
4. Compute \(P'_i = H_{\text{wots}}(p'_0\parallel\cdots\parallel p'_{44})\).
5. Compute \(L'_i = H_{\text{leaf}}(i\parallel P'_i)\).
6. Climb the auth path to a root \(R'\).
7. Accept iff \(R'=R\) and the checksum is valid.

## 3. Assumptions

1. **Preimage resistance:** given \(y\), it is infeasible to find \(x\) with \(F(x)=y\).
2. **Collision resistance:** it is infeasible to find \(x\ne x'\) with \(H_d(x)=H_d(x')\).
3. **Domain separation:** the contexts above are distinct and fixed.
4. **Stateful leaf invariant:** the signer never uses a leaf twice and never rolls back the counter.

These are explicit assumptions. They are not hidden behind a standard or an external audit.

## 4. Security proof

### Lemma 1 — WOTS one-time unforgeability

Let \(A\) be an adversary that receives the WOTS public key for leaf \(i\) and one
signature on message \(m\), and outputs a valid signature on \(m'\ne m\) for the
same leaf. Then we can find a preimage of \(F\) or a collision in one of the hash
functions.

**Proof.** Let \(d\) and \(d'\) be the digit vectors for \(m\) and \(m'\). If
\(m'\ne m\), either some message digit decreases, or some message digit
increases. In the latter case the checksum decreases, and at the first
differing checksum digit the smaller checksum has a smaller digit. Therefore
there is at least one index \(j\) with \(d'_j<d_j\).

Guess \(j\) and \(d'_j\); this succeeds with probability at least
\(1/(45\cdot63)\). Embed a random challenge \(z=F(x)\) at chain step
\(d'_j+1\), compute the public chain end forward from \(z\), and choose all
other chains normally. If \(d_j\le d'_j\), abort; otherwise compute the signing
value at step \(d_j\) by iterating forward from \(z\). The simulation is
distributed as the real signature.

The forgery supplies \(y\) at step \(d'_j\). Verification gives

\[
F^{63-d'_j}(y)=p_j=F^{63-d'_j}(x).
\]

If \(y=x\), we have a preimage of \(z=F(x)\). If \(y\ne x\), following the two
chains until they meet yields a collision in \(F\). The reduction loses at most
a factor \(45\cdot63=2835\). ∎

### Lemma 2 — WOTS key-only unforgeability

For an unused leaf, the adversary receives only \(P_i\). A valid signature
yields chain values whose forward hashes equal the \(p_{i,j}\). Producing them
without a signing query requires either a preimage of \(F\) at some chain step
or a collision in \(H_{\text{wots}}\). This is the same argument as Lemma 1 with
no signing query; it is at least as hard. ∎

### Lemma 3 — Merkle tree unforgeability

Assume the adversary can produce a valid signature for a leaf \(i'\) and message
\(m'\) that was not signed. Then either:

- \(i'\) is a leaf that was never used, and the WOTS signature is a key-only
  forgery (Lemma 2); or
- \(i'\) was used for a different message, and the WOTS signature is a one-time
  forgery (Lemma 1); or
- the authentication path produces a different leaf/root relation, which yields
  a collision in \(H_{\text{leaf}}\) or \(H_{\text{node}}\).

In all cases, the forgery reduces to Lemma 1, Lemma 2, or a hash collision. ∎

### Theorem — QHS-2 EUF-CMA

For at most 256 signing queries, QHS-2 is existentially unforgeable under
chosen-message attack, assuming:

- BLAKE3 is preimage- and collision-resistant for the domain-separated contexts;
- the stateful leaf invariant holds.

**Proof.** Each query consumes a distinct leaf. A forgery is either for a used
leaf (Lemma 1), an unused leaf (Lemma 2), or a different Merkle path (Lemma 3).
The reduction loss is at most \(256\cdot45\cdot63\approx 2^{19.47}\), which is
absorbed by the 256-bit hash output. ∎

## 5. Concrete security

- BLAKE3 output: 256 bits.
- WOTS preimage security: ≈256 bits minus the reduction loss (~19.5 bits) → ≈236.5 bits.
- Merkle collision security: ≈128 bits (birthday bound on 256-bit hashes).
- Overall classical target: ≥128 bits.
- Quantum: Grover preimage ≈2^128; collision ≈2^85–2^128 depending on the model; the conservative target is ≥64 bits.

The overall security is therefore at least the 128-bit classical target, with a
large preimage margin and a 128-bit collision bound.

## 6. Stateful-key invariant

QHS-2 is a **stateful** signature scheme. Reusing a leaf for two different
messages breaks WOTS one-time security.

Rules:

1. The private key carries `next_leaf`.
2. `sign` refuses when `next_leaf >= 256`.
3. The caller must persist the updated private key atomically after every signature.
4. Cloning, restoring an old private key, or concurrent signing with the same key is forbidden.
5. After 256 signatures, generate a new key.

The implementation enforces (1)–(3) in the API; (4)–(5) are operational
requirements documented in the FAD and CLI.

| Tamper/wrong message/wrong key rejected | attack suite |
| Key exhaustion rejected | attack suite |

| Cache validation and fallback | CLI cache header/tamper/foreign/oversized tests |

### 7.1 Performance implementation (non-normative)

QHS-2 uses the same implementation optimizations as QHS-1:

1. **Public-leaf cache.** 256 public Merkle leaves in an optional 8,232-byte
   file, with header `[2, 2, 8, 0]` and fingerprint context
   `qWp QHS-2 cache fingerprint`. It contains no secret WOTS values.
2. **Parallel keygen.** The 256 independent leaves are derived on up to 16 host
   threads.
3. **Cached signing.** `sign_with_leaves` uses the leaves only for the
   authentication path; the WOTS signature still comes from the secret seed.

Measured on the 16-thread reference host, release build:

| Operation | QHS-2 |
|---|---:|
| Keygen | ≈27–28 ms |
| Sign | ≈0.46–0.61 ms |
| Verify | ≈0.41 ms |

The timing harness reports Welch \(|t| < 4.5\) for keygen and signing across two
secret seeds. The QHS-2 KAT signature hash is
`159fb7dd8498d70589da6e4ea1c52d00d86ca070e028ebcbcfa30fd083dd9385`.

## 8. Limitations

- BLAKE3 security is an assumption; qWp implements and tests BLAKE3 but does not prove its cryptographic hardness.
- The proof is a written reduction, not a machine-checked cryptographic proof.
- The scheme is stateful and limited to 256 signatures per key.
- QHS-2 is newer and has less deployment evidence than QHS-1; QHS-3/3.1 are newer still.
- No standard compliance claim is made.
- The braid/Jones engine is a research module and is not part of the QHS-2 security argument.

## 9. Attack plan

1. Forge a signature for a used leaf (Lemma 1 attack).
2. Forge for an unused leaf (key-only WOTS attack).
3. Tamper with auth path/leaf index.
4. Reuse a leaf by rolling back the counter (must be prevented operationally).
5. Exhaust the key and verify rejection.
6. Cross-domain hash confusion between QHS-1, QHS-2, QHS-3, and QHS-3.1.
7. Cache poisoning / foreign-cache injection.
8. Timing/fault/DoS.
9. Measure the best-known attack cost and publish it.

If any attack succeeds, QHS-2 is broken; fix or stop. No standard fallback.
